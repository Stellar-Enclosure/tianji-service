# Tianji Service

Tianji is the business process and intelligent orchestration platform for Stellar Enclosure. The current delivery contains engine-neutral contracts, a PostgreSQL Agent ledger, a manually invoked single-run executor, an opt-in secured Agent HTTP adapter, and an independent Flowable process host with an opt-in initial API. A background Agent dispatcher and the remaining process and runtime capabilities are still being built.

## Modules

- `stellar-enclosure-tianji-contract`: JDK-only Agent, process and decision contracts.
- `stellar-enclosure-tianji-client`: engine-neutral HTTP clients and resumable Agent event stream.
- `stellar-enclosure-tianji-agent-runtime`: the embedded runtime boundary and transactional Agent ledger; disabled by default.
- `stellar-enclosure-tianji-agent-server`: Spring Boot host and disabled-by-default Agent HTTP/SSE adapter.
- `stellar-enclosure-tianji-process-server`: isolated Flowable 8 BPMN/CMMN/DMN host, single-database JDBC Outbox and disabled-by-default process API.

The selected dependency line is Java 25, Spring Boot 4.1.2, Spring AI 2.0.2, Google ADK 1.13.0 and Flowable OSS 8.0.0. The Agent runtime uses Agent Flow `0.0.2-SNAPSHOT`, and the Process Server uses the JDBC Outbox `0.0.2-SNAPSHOT`; until those artifacts are published, build them together with the Components source repository. Contract and client modules do not depend on either engine or an AI framework; the Process Server does not depend on the Agent runtime.

The client uses JDK `HttpClient` and Jackson 3. Construct `HttpAgentClient` with a service URI, a client configured with `Redirect.NEVER`, a supplier of the current access token, a request timeout and a bounded event-stream reconnect policy. It sends writes once, limits JSON responses and resumes SSE using the last delivered persisted sequence. A subscriber controls demand and may cancel its subscription without cancelling the Agent run. A `stream.complete` frame closes a terminal stream; a planned `stream.reconnect` rotates the connection without treating it as a failed run; an expired cursor is reported as `TIANJI_EVENT_CURSOR_EXPIRED`. Error bodies and access tokens are not retained in client exceptions. The client has been tested against local HTTP stubs; real deployment integration remains to be verified.

The engine-neutral `ProcessReleaseClient`, `ProcessClient` and `DecisionClient` contracts have a JDK HTTP implementation in `HttpProcessClient`. It sends writes once, bounds request/response sizes and deadlines, and checks the returned release version, model hashes and request correlation. Its transport has been tested with local stubs; the server adapter has also been exercised with MockMvc and a disposable PostgreSQL database, while real identity services and a deployed network path remain to be verified.

The HTTP adapter is disabled by default. Enabling `stellar.tianji.agent.api.enabled` requires a servlet application, a configured ledger, the Tianquan-Shoubing and Tianquan-Jianshen filters and the compiled permission policy. It derives tenant and subject exclusively from verified USER or tenant-scoped SERVICE identity and checks the resource policy before accessing the ledger. The run list uses an exclusive cursor ordered by creation time and run ID and exposes only the caller's own runs; refresh from the first page to include newly created runs. No permission is granted by building the application. SSE keeps the verified request context for repeated authorization, allows at most 32 simultaneous streams, reads at most eight events per page and rotates connections after 30 seconds. Deployment must also bound servlet and proxy write timeouts for slow or disconnected clients. A result that has not yet been committed returns `TIANJI_RESULT_NOT_READY` with HTTP 409.

A browser may send `X-Egon-Tianji-Tenant` as an expected-context assertion; a mismatch returns `TIANJI_TENANT_CONTEXT_CHANGED` and never selects or grants a tenant. Verified tenant IDs must be canonical positive decimal values that fit a signed 64-bit integer.

`stellar.tianji.agent.runtime.enabled` is false by default. Setting it to true currently fails startup because scheduling and complete runtime assembly are not yet wired into the service. No Agent or process endpoint is enabled by default. The ledger accepts an internal `TrustedAgentActor`; a caller must authenticate and authorize before creating it. Input artifact references and policy overrides are requests, not authorization; the ledger only permits policy limits to be reduced.

The ledger stores immutable definition versions, scoped idempotent starts, run status and ordered events. Its additive migrations are in `classpath:db/tianji-agent`; they are not run automatically. A deployment must use a dedicated Flyway configuration and schema owner for `tianji_agent`, separate from any other application's migration history. A host can dispatch a selected queued run through a bounded executor; cancellation and lease recovery are persisted, but periodic discovery and complete service wiring are still pending. The executor accepts text input and rejects artifact references, structured task data and tools until their governance is ready. A host can enable persistent sessions for the manually selected run by supplying the exact same `DataSource` used by the ledger to the executor's session-aware constructor. The original constructor keeps session-backed runs unavailable. Code-first factories must be registered by trusted application code and use the supplied context-aware scheduler for every parallel agent.

Claims use PostgreSQL time and a fencing epoch; an expired lease is suspended for reconciliation rather than automatically retried. Cancellation intent and its command receipt commit together, and the worker polls the persisted intent while executing. The host supplies and owns the bounded dispatch executor and control scheduler. It must also supply a thread-safe, provider-specific `AgentModelBudgetEstimator` that conservatively bounds input tokens, output tokens and cost and can interpret verified provider usage. Reservations are atomic across parallel branches, unknown usage retains its allowance, and unavailable required usage fails the run. The provider must honor the requested output limit; an overrun can only be detected after the provider reports it. Total and per-model idle deadlines are enforced independently.

Ledger reconciliation can be enabled separately with `stellar.tianji.agent.reconciliation.enabled=true`. The host must provide an `AgentLedgerService` and a managed `TaskScheduler` bean named `tianjiAgentReconciliationScheduler`; missing dependencies fail startup. `batch-size` defaults to 100 (1–1,000), `interval` to 5 seconds (250 ms–1 hour), and `shutdown-timeout` to 5 seconds (0–30 seconds). Each poll only expires overdue runs or suspends expired running leases, using the existing database revision checks; it never claims queued work, calls a model, or manufactures a delegated identity. Polls do not overlap within one instance, and shutdown waits up to the configured bound. This does not enable the Agent runtime or provide periodic dispatch.

`TEXT_DELTA` events are increments, while `AGENT_OUTPUT` events are complete snapshots for individual Agents; neither is the root completion signal. The projector accepts only authors from the compiled Agent tree and excludes native parts marked as thoughts and tool arguments. Provider-specific text may still contain sensitive content and requires the later authorization and redaction controls. The final run status is written after the root stream finishes. A single execution snapshot or event is limited to 1 MiB of UTF-8 JSON, and a final result to 2 MiB; oversized values fail rather than being silently truncated.

The Agent database migration V3 adds an internal PostgreSQL implementation of ADK's `BaseSessionService`. A trusted host binds it to one tenant, principal and application; `app:` state is tenant/application scoped and requires explicit host authorization to write, `user:` state is additionally principal scoped, and `temp:` state is not persisted. New runs referencing a session must own an existing session in the `tianji` application. Active runs or leases prevent deletion. Existing queued runs created before V3 may reference sessions that do not exist and require review; migration does not silently create or rewrite them. Each durable event append checks both the live AgentRun lease and a separate database-timed session lease, stores the native event and state change in one transaction, rejects stale snapshots, and treats an identical event identifier/content as a replay. Authentication configuration, partial events and values that cannot round-trip without loss are not stored. Session history reads are bounded to 1,000 events and 8 MiB; application and user state are each bounded to 500 entries and 4 MiB.

Migration V4 adds version markers for session and scoped state. The upgraded reader supports both the V3 format and an explicitly typed format that preserves JSON-compatible Java numeric types in state, event values, tool exchanges and compacted content. Existing constructors keep writing the V3 format, which rejects numeric types that ADK's JSON mapper cannot restore exactly. Apply V4 and upgrade **all** session readers and writers before enabling typed writes through the `typedWrites` constructor argument on `PostgresAdkSessionService` or `typedSessionWrites` on `AdkAgentRunExecutor`. Older binaries cannot safely read typed data, so do not roll them back or run them concurrently after the switch. Disabling typed writes on upgraded binaries does not rewrite existing typed values; a later legacy-format write that cannot preserve them fails rather than dropping type information.

Agent migration V5 binds run, cancellation and session ownership to a fingerprint of the verified issuer as well as tenant and subject. Existing records remain in the separate `LEGACY` namespace; a newly verified identity cannot automatically claim them. V5 changes uniqueness and session foreign keys, so stop old Agent readers and writers, apply the migration in a planned maintenance window, and upgrade all nodes before enabling the API or new issuer-bound writes. If legacy records need to be assigned to verified identities, first establish an authoritative mapping and use a separately reviewed migration. The API captures the issuer from the verified request before RBAC replaces the USER authentication token and requires the authorization snapshot to match it; no bearer credential is persisted.

The session-aware manual executor acquires a session lease after claiming the run, renews both while executing, and releases the session lease after shutdown. A competing run fails explicitly with `TIANJI_SESSION_BUSY` before calling the model. Losing a session lease interrupts the model and leaves the run for normal lease reconciliation rather than recording success. The complete background runtime is not yet wired and remains disabled by default. Database tests exercise the adapter and executor with a real ADK Runner and a fake model. Apply V3 through the dedicated AgentDB migration process, not through the application at startup.

The opt-in Agent HTTP adapter provides session metadata operations at `/api/tianji/v1/agent-sessions`: `PUT` with a caller-supplied `sessionId` creates or returns the owned session without replacing its history; `GET` lists owned sessions; `GET /detail` queries one; `DELETE` removes one only when no run or lease is active. The identifier is a query parameter for the individual operations. The API returns metadata rather than native ADK events or state. Creation requires both `TIANJI_AGENT_START` and `TIANJI_AGENT_READ`; reading requires `TIANJI_AGENT_READ`; deletion requires `TIANJI_AGENT_READ` and the separately granted `TIANJI_SESSION_DELETE`, with their matching OAuth scopes. Registration and grants are separate deployment operations.

Session-backed run starts use `POST /api/tianji/v1/agent-runs/with-session`, whose single authorization decision requires both start and read permissions and scopes. The original `POST /api/tianji/v1/agent-runs` remains the one-shot endpoint and now rejects a non-null session ID; callers using raw HTTP for the previously accepted but unexecutable session request must switch paths. `HttpAgentClient.start` selects the correct path automatically, and its `AgentSessionClient` methods send each mutation once without application-level replay. A client can repeat the same create ID after an uncertain response; after an uncertain delete it should query the session before deciding what to do next.

## Process Server storage baseline

The Process Server owns a separate PostgreSQL database/schema and shares one local `DataSource` and transaction manager between its Flowable engines and JDBC Outbox. Its default schema is `tianji_process`; configure the JDBC connection's search path to select that same schema. Startup rejects a different schema, transaction manager or data source, disabled Outbox validation, automatic Flowable schema changes, Spring SQL initialization and automatic Flyway migration. The process API is disabled by default, and a servlet host without it only exposes health. The Flowable IDM and Event Registry engines, automatic definition deployment, asynchronous job executors and Outbox polling are disabled by default. No Outbox delivery channel is configured yet. Disabling polling does not suppress the component's immediate post-commit wake-up; configure and verify a delivery channel before enqueuing production messages.

Before deployment, an operator must provision a dedicated schema with Flowable 8.0.0's official PostgreSQL schema/upgrade artifacts and the Outbox starter's unchanged `db/transactional-outbox/postgresql/V1__create_transactional_outbox_schema.sql`, using separate controlled migration histories and a schema owner. Configure a runtime role without schema creation privileges; the application never initializes or upgrades those tables, but does not create or manage database roles. This repository does not yet provide a production schema-provisioning command; the integration test initializes only its isolated empty database. The Process Server must not use the Agent-owned schema or tables; a separate logical database is preferred. Outbox messages require a tenant-scoped idempotency key and a trusted tenant in the event; delivery remains at least once.

The engines do not expose Spring beans to model expressions. `ProcessModelValidator` validates bounded UTF-8 XML against packaged Flowable schemas and a closed allowlist before release deployment. Its BPMN subset supports acyclic start/end, user tasks, bounded parallel gateways and constant timers; DMN supports one decision table with string, boolean and at most 15-digit integer literals, and FIRST/UNIQUE/ANY hit policies. Decimal rules, external-worker tasks and CMMN imports require later validation and are not included yet. Flowable 8's ordinary decision builder can fall back to the latest same-tenant definition when a parent deployment is missing, and the tested audit result does not populate its deployment ID; that builder alone cannot enforce a fixed release.

The optional decision-task subset adds one Flowable DMN service task and a bounded exclusive split immediately after it. The task references a decision by a literal `decisionTableReferenceKey`; both models must belong to the same immutable release. Each decision input must have the same name and type in the process input schema, and outputs must not overwrite process inputs. A split has an explicit default and only equality comparisons between one declared decision output and bounded primitive literals. Scripts, arbitrary expressions, other extension fields, parallel gateways in a decision-task model and unsupported graph shapes are rejected. On no hit, decision outputs are set to null and the default route is used. Equal multi-hit outputs are accepted; inconsistent outputs fail the transaction. The exact process and decision definitions, tenant, version and model hashes are rechecked at execution, and decision history is committed with the process transition. The fixture `approval-routing.bpmn20.xml` illustrates the supported form.

Publishing models with decision tasks is disabled by default. Set `stellar.tianji.process.decision-tasks.enabled=true` on API nodes only after **all** Process Server nodes, including timer and job executors, run a version containing the pinned decision behavior and have synchronous DMN history enabled. Existing published instances can continue when publication is disabled. DMN tasks deployed outside a Tianji release cannot be resolved by the pinned behavior and fail closed; inventory and migrate any such unmanaged instances before upgrading. Do not run or roll back to an older Process Server after enabling this feature: an older engine can use Flowable's latest-version fallback. This switch does not register permissions or enable the Process API.

The internal `FlowablePinnedDecisionExecutor` replaces that fallback with an exact definition-ID lookup inside Flowable's command, checks the bound tenant, key, deployment, version and validated XML, then checks the decision audit inside the same JDBC transaction. It accepts only the validated input names and primitive types, returns immutable values and rolls back a failed decision. Its binding must come from a separately authorized tenant-scoped release; the adapter does not grant access, manage releases or expose an HTTP/SDK endpoint.

The internal `ProcessReleaseService` atomically deploys validated BPMN/DMN resources and records immutable, tenant-scoped definition IDs, versions, model hashes and input schemas. An identical release key and manifest is idempotent; a different manifest conflicts. It serializes concurrent deployments of the same tenant/model key so Flowable versions remain distinct.

The platform release/command tables have separate migrations under `db/tianji-process`: V1 creates release and receipt tables, V2 adds decision result receipts, and V3 binds publisher and command ownership to an issuer fingerprint without changing earlier migrations. Use the `tianji_process_schema_history` Flyway history for this location, distinct from Outbox's history and Flowable's own schema history. Because the shared schema already contains engine and Outbox tables, the isolated integration test explicitly creates the new history with a version-0 baseline before applying platform V1. Production provisioning requires an operator-controlled equivalent after checking the target history and platform tables; the application still performs no automatic migration.

V3 retains pre-existing ownership in a separate `LEGACY` namespace. New HTTP identities use a fingerprint of the verified issuer and cannot automatically claim those records. Upgrade every process reader and writer before enabling the API; old binaries that ignore issuer affinity must not run alongside new issuer-bound writes. If legacy records need to become available to verified identities, an operator must first establish an authoritative mapping and plan a separate controlled migration. V3 changes the receipt primary key and therefore needs an appropriately planned database migration window.

The internal `ProcessExecutionService` starts a process by the exact tenant-scoped release binding after rechecking its deployed model and input schema. The start receipt and Flowable instance commit together; the same actor and command ID replay the existing instance, while changed input conflicts. Its query is restricted to the initiating actor and tenant and uses synchronous Flowable instance history for completed or cancelled instances.

The internal `ProcessDecisionService` evaluates a release-bound DMN without creating a BPMN instance. It stores the decision's scoped history and result receipt in the same transaction, so a repeated actor/request ID returns the original result without evaluating again. Rule IDs come from the model; a rule without an explicit ID is identified by its stable `row:<one-based number>` within that immutable release. Decision input values are present in Flowable's decision history; retention and redaction controls remain future work.

Set `stellar.tianji.process.api.enabled=true` only in an explicitly configured servlet host. The source provides `POST /api/tianji/v1/process-releases`, `GET /api/tianji/v1/process-releases/{releaseVersion}`, `POST /api/tianji/v1/process-instances`, `GET /api/tianji/v1/process-instances/{instanceId}` and `POST /api/tianji/v1/decisions/evaluate`. The adapter requires verified Tianquan-Shoubing USER or tenant-scoped SERVICE identity, the Tianquan-Jianshen guard, and respectively `TIANJI_PROCESS_RELEASE_PUBLISH`, `TIANJI_PROCESS_RELEASE_READ`, `TIANJI_PROCESS_START`, `TIANJI_PROCESS_READ`, or `TIANJI_DECISION_EXECUTE` with their matching OAuth scopes. Tenant, subject and issuer never come from request bodies; instance reads remain owner-scoped. Registration, activation and role/client grants are separate deployment steps and are not performed by the build.

The current checks cover the resource permission, OAuth scope, tenant and instance owner. Business-specific object and data scopes are not yet applied, and the initial model subset does not execute external workers or business writes.

The engine-neutral Worker contract and HTTP client define one-task acquisition and completion/failure receipts, but the corresponding Process Server endpoints and Worker Starter are **not implemented yet**. No Worker capability is enabled by these types. Acquisition derives tenant from the authenticated service identity, and an uncertain acquisition may leave a lease until it expires. An accepted completion or failure can be replayed with the exact same lease and payload; an unknown side effect requires manual reconciliation. A receipt ID alone does not prove business idempotency: the eventual Worker integration must commit the business change and its receipt in the same business transaction or use an external system's verified idempotency mechanism. Lease tokens and task data are redacted from the contract objects' string representations.

The validator recognizes a candidate external-worker model with a literal topic, a versioned schema, `doNotIncludeVariables=true` and explicit typed input/output mappings, illustrated in `worker-mapping.bpmn20.xml`. The current mapping check allows inputs only from declared process inputs and rejects output names that overwrite those inputs or other decision/worker outputs. This validation is preparatory: release publishing rejects any model containing an external-worker task until the secured Worker adapter is available.

Enabling the API performs read-only checks of platform Flyway checksums, columns, key constraints and the start receipt index; the runtime role needs SELECT on `tianji_process_schema_history` and the PostgreSQL catalog. These checks and the engine/API integration have been exercised against PostgreSQL 18.3; other PostgreSQL versions and real identity/permission services require separate acceptance. The adapter bounds JSON request bodies to 9 MiB and does not install schema or publish permissions at startup.

For a JDK 25 environment with the Stellar-Enclosure platform parent and Components BOM available in Maven, run this from the repository root. It builds the sibling Components, Tianquan-Shoubing and Tianquan-Jianshen checkouts and Tianji in one reactor without installing or publishing artifacts:

```bash
./scripts/verify-source-reactor.sh -B -ntp
```

Set `STELLAR_COMPONENTS_DIR`, `STELLAR_SHOUBING_DIR` or `STELLAR_JIANSHEN_DIR` when the repositories are not sibling checkouts. The script requires Python 3 only to create a temporary reactor POM. After matching versioned Agent Flow and identity/authorization artifacts are available in the configured Maven repository, `./mvnw -B -ntp test` can also build Tianji on its own.

The `permission-producer` build profile uses Tianquan-Jianshen's processor and manifest CLI to embed and verify each server's resource declarations in its executable JAR. Agent and Process use nonoverlapping resource-key prefixes. A release build must supply the exact source commit and a unique build identity; generating a manifest neither activates it nor assigns permissions:

```bash
STELLAR_VERIFY_GOAL=verify ./scripts/verify-source-reactor.sh -B -ntp -Ppermission-producer \
  -Dpermission.commit="$(git rev-parse HEAD)" -Dpermission.buildId="<build-identity>"
```

The default tests use in-memory Spring contexts and a temporary loopback HTTP stub; they do not start the application server and they skip PostgreSQL integration classes. To run the runtime database tests, supply an explicitly created empty loopback database named `tianji_it_*` through `-Dtianji.postgres.test.url=jdbc:postgresql://127.0.0.1:<port>/tianji_it_<name>`. The HTTP ledger test uses a second independently created empty database through `-Dtianji.http.postgres.test.url` with the same URL restrictions. The tests reject any other URL and refuse a database that already contains the `tianji_agent` schema. They apply the migration and include concurrent starts, scope isolation, transaction rollback, HTTP replay and real ADK Runner execution with a fake model. Use disposable test databases, never a shared or production database.

The Process Server integration test similarly requires a separate empty loopback database through `-Dtianji.process.postgres.test.url` and a dedicated, non-superuser login named `tianji_it_runtime_<12 lowercase hex digits>` through `-Dtianji.process.postgres.test.runtime-user`. It refuses an existing process schema, grants that temporary role access only to the newly created schema, and checks that the role cannot create schema objects. The test provisions Flowable and Outbox in the disposable database, exercises BPMN/Timer, CMMN and independent DMN, verifies same-transaction commit and rollback, and reconstructs the engines to check persisted state. It explicitly enables the native Job Executor inside a short-lived test context to verify that a persisted timer completes after reconstruction, then verifies executor shutdown. It does not test production migration or a deployed service.

Real model providers, MCP, full service execution and process engines require separate integration and acceptance work.
