# Tianji Service

Tianji is the business process and intelligent orchestration platform for Stellar Enclosure. The current delivery contains engine-neutral contracts, a PostgreSQL Agent ledger, a manually invoked single-run executor, an opt-in secured Agent HTTP adapter, and an independent Flowable process host with an opt-in initial API. Opt-in background discovery requires explicit host wiring; the remaining process and runtime capabilities are still being built.

## Modules

- `stellar-enclosure-tianji-contract`: JDK-only Agent, process and decision contracts.
- `stellar-enclosure-tianji-client`: engine-neutral HTTP clients and resumable Agent event stream.
- `stellar-enclosure-tianji-agent-runtime`: the embedded runtime boundary and transactional Agent ledger; disabled by default.
- `stellar-enclosure-tianji-agent-server`: Spring Boot host and disabled-by-default Agent HTTP/SSE adapter.
- `stellar-enclosure-tianji-process-server`: isolated Flowable 8 BPMN/CMMN/DMN host, single-database JDBC Outbox and disabled-by-default process API.

The selected dependency line is Java 25, Spring Boot 4.1.2, Spring AI 2.0.2, Google ADK 1.13.0 and Flowable OSS 8.0.0. The Agent runtime uses Agent Flow `0.0.2-SNAPSHOT`, and the Process Server uses the JDBC Outbox `0.0.2-SNAPSHOT`; until those artifacts are published, build them together with the Components source repository. Contract and client modules do not depend on either engine or an AI framework; the Process Server does not depend on the Agent runtime.

The client uses JDK `HttpClient` and Jackson 3. Construct `HttpAgentClient` with a service URI, a client configured with `Redirect.NEVER`, a supplier of the current access token, a request timeout and a bounded event-stream reconnect policy. It sends writes once, limits JSON responses and resumes SSE using the last delivered persisted sequence. A subscriber controls demand and may cancel its subscription without cancelling the Agent run. A `stream.complete` frame closes a terminal stream; a planned `stream.reconnect` rotates the connection without treating it as a failed run; an expired cursor is reported as `TIANJI_EVENT_CURSOR_EXPIRED`. Error bodies and access tokens are not retained in client exceptions. The client has been tested against local HTTP stubs; real deployment integration remains to be verified.

The engine-neutral `ProcessReleaseClient`, `ProcessClient` and `DecisionClient` contracts have a JDK HTTP implementation in `HttpProcessClient`. It sends writes once, bounds request/response sizes and deadlines, and checks the returned release version, model hashes and request correlation. Its transport has been tested with local stubs; the server adapter has also been exercised with MockMvc and a disposable PostgreSQL database, while real identity services and a deployed network path remain to be verified.

The HTTP adapter is disabled by default. Enabling `stellar.tianji.agent.api.enabled` requires a servlet application, a configured ledger, the Tianquan-Shoubing and Tianquan-Jianshen filters and the compiled permission policy. It derives tenant and subject exclusively from verified USER or tenant-scoped SERVICE identity and checks the resource policy before accessing the ledger. The run list uses an exclusive cursor ordered by creation time and run ID and exposes only the caller's own runs; refresh from the first page to include newly created runs. No permission is granted by building the application. SSE keeps the verified request context for repeated authorization, allows at most 32 simultaneous streams, reads at most eight events per page and rotates connections after 30 seconds. Deployment must also bound servlet and proxy write timeouts for slow or disconnected clients. A result that has not yet been committed returns `TIANJI_RESULT_NOT_READY` with HTTP 409.

A browser may send `X-Egon-Tianji-Tenant` as an expected-context assertion; a mismatch returns `TIANJI_TENANT_CONTEXT_CHANGED` and never selects or grants a tenant. Verified tenant IDs must be canonical positive decimal values that fit a signed 64-bit integer.

`stellar.tianji.agent.runtime.enabled` is false by default. When explicitly enabled, it assembles the ledger, ADK executor and a dedicated dispatcher only after the host supplies the required storage, authorization, model and execution resources. No Agent or process endpoint or periodic dispatcher is enabled by this switch. The ledger accepts an internal `TrustedAgentActor`; a caller must authenticate and authorize before creating it. Input artifact references and policy overrides are requests, not authorization; the ledger only permits policy limits to be reduced.

The standalone Agent Server includes PostgreSQL JDBC and Spring Boot JDBC support, but does not create a DataSource by default. Set `stellar.tianji.agent.storage.enabled=true` and provide the usual `spring.datasource` connection settings externally to create the pooled DataSource and ledger; a host-provided DataSource can be used instead. The database and `tianji_agent` schema must already be provisioned and migrated. Startup checks the schema without changing it; the server defaults disable Flyway and Spring SQL initialization. Its database role must have the required table and catalog permissions, and the operator must ensure that every connection consistently reaches the same writable primary. Enabling storage alone does not enable an API, execution or scheduling.

The ledger stores immutable definition versions, scoped idempotent starts, run status and ordered events. Its additive migrations are in `classpath:db/tianji-agent`; they are not run automatically. A deployment must use a dedicated Flyway configuration and schema owner for `tianji_agent`, separate from any other application's migration history. A host can dispatch a selected queued run through a bounded executor; cancellation and lease recovery are persisted, and periodic discovery has its own opt-in switch. Execution requires a host-supplied `AgentRunAuthorization` verifier of a revocable, run-bound grant and current permissions, checked before claiming and again before each model call. The request includes the verified issuer fingerprint, tenant, subject, run ID and immutable definition, input and policy fingerprints; it contains no bearer token or prompt text. Legacy actors and the old constructors without a verifier fail closed. If authorization is unavailable before claim, the run remains queued; a confirmed denial suspends it without claiming. If it is denied or unavailable after claim, the active lease is fenced and the run is suspended for explicit recovery; outstanding usage remains unknown. The server's verifier is the opt-in Jianshen execution-decision client described below. The executor accepts text input and rejects artifact references, structured task data and tools until their governance is ready. It also rejects definitions that declare prompt, skill or tool dependencies until those exact versions can be resolved and governed; they are not silently omitted. A host can enable persistent sessions for a manually constructed executor by supplying the exact same `DataSource` used by the ledger to its session-aware constructor. The original constructor keeps session-backed runs unavailable. Code-first factories must be registered by trusted application code and use the supplied context-aware scheduler for every parallel agent. Agent-level before-model callbacks are rejected because ADK invokes them after the budget plugin and they can modify the metered request; they remain unavailable until governance can inspect the final request.

For automatic assembly, enable `egon.cola.component.agent-flow.enabled=true` and `egon.cola.component.agent-flow-registry.enabled=false`; Tianji reads definitions from its own ledger instead of a static Agent Flow registry. Supply a direct PostgreSQL `DataSource`, at least one named `ChatModel` or a trusted map bean named `tianjiAgentCodeFirstFactories`, a current `AgentRunAuthorization`, and a provider-specific `AgentModelBudgetEstimator`. The server's grant and execution-authorization switches supply its USER verifier. The standalone server creates dedicated bounded dispatch and control executors when runtime is enabled; an embedded host supplies them, and either host may explicitly replace the named beans. `tianjiAgentDispatchExecutor` must be a `ThreadPoolExecutor` with at most 128 threads and a queue of at most 128 entries; `tianjiAgentControlExecutor` must be a separate `ScheduledThreadPoolExecutor` with 1–128 core threads and remove-on-cancel enabled. Both use `AbortPolicy`; incompatible resources fail startup. Server defaults are 4 dispatch threads, a queue of 4 and 4 control threads, configurable through `dispatch-threads`, `dispatch-queue-capacity` (0–128) and `control-threads` under `stellar.tianji.agent.runtime`. Its dedicated threads do not inherit request thread-local values. The auto-configured executor uses the exact ledger DataSource for sessions and checks the provisioned schema before use. `stellar.tianji.agent.runtime.typed-session-writes` defaults to false; enable it only after the coordinated V4 reader upgrade described below. The host is responsible for stable model routing and lifecycle shutdown of any supplied pools. This wiring does not configure a production model, estimate provider tokens, register permissions or enable periodic dispatch.

Claims use PostgreSQL time and a fencing epoch; an expired lease is suspended for reconciliation rather than automatically retried. Cancellation intent and its command receipt commit together, and the worker polls the persisted intent while executing. The host supplies and owns the bounded dispatch executor and control scheduler. It must also supply a thread-safe, provider-specific `AgentModelBudgetEstimator` that conservatively bounds input tokens, output tokens and cost and can interpret verified provider usage. For each model call the estimator must resolve the context window and safety margin for the exact model, model-route reference and policy version fixed in the run; it must include system instructions, history, tool schemas and provider-adapter additions in its estimate. An adapter that does not implement `contextWindow` now fails closed. The runtime rejects a request when estimated input plus the effective output limit and safety margin exceed the window, or when the resolved window changes within the run. The host must retain immutable versions across restarts; the runtime does not yet trim history or store context provenance. Reservations are atomic across parallel branches, unknown usage retains its allowance, and unavailable required usage fails the run. The provider must honor the requested output limit; an overrun can only be detected after the provider reports it. Total and per-model idle deadlines are enforced independently.

Ledger reconciliation can be enabled separately with `stellar.tianji.agent.reconciliation.enabled=true`. It requires an `AgentLedgerService` and a managed `TaskScheduler` bean named `tianjiAgentReconciliationScheduler`; the standalone server creates a dedicated scheduler if the host has not supplied one. `batch-size` defaults to 100 (1–1,000), `interval` to 5 seconds (250 ms–1 hour), and `shutdown-timeout` to 5 seconds (0–30 seconds). Each poll only expires overdue runs or suspends expired running leases, using the existing database revision checks; it never claims queued work, calls a model, or manufactures a delegated identity. Polls do not overlap within one instance, and shutdown waits up to the configured bound. This does not enable the Agent runtime or provide periodic dispatch.

`TEXT_DELTA` events are increments, while `AGENT_OUTPUT` events are complete snapshots for individual Agents; neither is the root completion signal. The projector accepts only authors from the compiled Agent tree and excludes native parts marked as thoughts and tool arguments. Provider-specific text may still contain sensitive content and requires the later authorization and redaction controls. The final run status is written after the root stream finishes. A single execution snapshot or event is limited to 1 MiB of UTF-8 JSON, and a final result to 2 MiB; oversized values fail rather than being silently truncated.

The Agent database migration V3 adds an internal PostgreSQL implementation of ADK's `BaseSessionService`. A trusted host binds it to one tenant, principal and application; `app:` state is tenant/application scoped and requires explicit host authorization to write, `user:` state is additionally principal scoped, and `temp:` state is not persisted. New runs referencing a session must own an existing session in the `tianji` application. Active runs or leases prevent deletion. Existing queued runs created before V3 may reference sessions that do not exist and require review; migration does not silently create or rewrite them. Each durable event append checks both the live AgentRun lease and a separate database-timed session lease, stores the native event and state change in one transaction, rejects stale snapshots, and treats an identical event identifier/content as a replay. Authentication configuration, partial events and values that cannot round-trip without loss are not stored. Session history reads are bounded to 1,000 events and 8 MiB; application and user state are each bounded to 500 entries and 4 MiB.

Migration V4 adds version markers for session and scoped state. The upgraded reader supports both the V3 format and an explicitly typed format that preserves JSON-compatible Java numeric types in state, event values, tool exchanges and compacted content. Existing constructors keep writing the V3 format, which rejects numeric types that ADK's JSON mapper cannot restore exactly. Apply V4 and upgrade **all** session readers and writers before enabling typed writes through the `typedWrites` constructor argument on `PostgresAdkSessionService` or `typedSessionWrites` on `AdkAgentRunExecutor`. Older binaries cannot safely read typed data, so do not roll them back or run them concurrently after the switch. Disabling typed writes on upgraded binaries does not rewrite existing typed values; a later legacy-format write that cannot preserve them fails rather than dropping type information.

Agent migration V5 binds run, cancellation and session ownership to a fingerprint of the verified issuer as well as tenant and subject. Existing records remain in the separate `LEGACY` namespace; a newly verified identity cannot automatically claim them. V5 changes uniqueness and session foreign keys, so stop old Agent readers and writers, apply the migration in a planned maintenance window, and upgrade all nodes before enabling the API or new issuer-bound writes. If legacy records need to be assigned to verified identities, first establish an authoritative mapping and use a separately reviewed migration. The API captures the issuer from the verified request before RBAC replaces the USER authentication token and requires the authorization snapshot to match it; no bearer credential is persisted.

Agent migration V6 adds an execution-grant evidence table. `AgentExecutionGrantStore` stores only the Shoubing-sealed ticket, its expiry and an immutable run-binding digest; it never stores the USER bearer. A database-fenced issuance epoch rejects delayed concurrent responses, and completion is accepted only while the same owned run remains queued and uncancelled. Reads require an unchanged active run, the exact issuer/tenant/subject/resource binding and an unexpired ticket. The default-off `stellar.tianji.agent.execution-grants.enabled` switch connects USER starts to Shoubing issuance after the queued run commits. Enabling it requires the Agent API, V6, the exact ledger DataSource and a trusted tenant/issuer authority binding with the dedicated issue scope. Startup reads the dedicated `tianji_agent.flyway_schema_history`, checks the V1–V6 checksums, required columns, identity collation and critical keys, and checks that the current PostgreSQL connection is writable and not a standby. The runtime role needs read access to that history and the PostgreSQL catalog. This one-time probe cannot prove that a routing proxy will always select the same primary; the operator must supply a direct, consistently routed primary DataSource and coordinate migrations separately. A failed or uncertain issue leaves the owned run queued; the caller may repeat the same start and idempotency key with a fresh verified USER token. A delayed issue response cannot attach to a cancelled or already claimed run. SERVICE execution uses the separate opt-in V8 path described below; it is excluded from discovery unless that path is enabled.

Agent migration V7 adds an internal process-dispatch fence. `AgentLinkedSubmissionService` accepts only a verified SERVICE actor supplied by a trusted host, binds one process or case occurrence to an immutable Agent definition hash and a submission deadline no more than 15 minutes away, and writes the link into the run snapshot in the same transaction as the fence and queued run. A close request can create a tombstone before a run exists; if a submission is already in its commit path, close waits on the same database fence and cancels the committed run before returning. A lock timeout is an unavailable result and must be retried. In-flight database commits may finish after the deadline, so the process side must durably retry close after cancellation or expiry; the deadline alone is not a cross-database commit barrier. Closing a running Agent records cancellation intent and cannot undo external work already started. The default-off linked HTTP adapter can resolve and close these fences for a configured SERVICE identity. The optional SERVICE delegation path is described below; Process-side durable dispatch and automatic reconciliation are not yet provided. Provision V7 separately and upgrade all Agent snapshot readers before creating linked runs; older readers do not understand the new snapshot field. The runtime role needs SELECT, INSERT and UPDATE on the fence table, and fence retention must cover all possible submission retries.

Agent migration V8 adds a separate SERVICE execution-grant table linked to the process-dispatch fence. After provisioning V8, `stellar.tianji.agent.service-execution.enabled=true` requires the secured Agent API, linked adapter, USER grant infrastructure and execution authorization. Configure finite `sources` entries with the exact `issuer`, `tenant-id`, `client-id` and original service `resource-uri`; these must match the linked source/definition bindings and the independent Shoubing and Jianshen SERVICE policies. The Agent service registration must be granted the separate Shoubing issue and Jianshen decision scopes, and USER issuance and decision scopes remain required by the existing shared authorization setup. For a linked submission, the verified SERVICE bearer is forwarded only to Shoubing while the request is active; only the sealed ticket, source tuple and immutable run digest are stored. Ticket publication serializes with process close, and claim/model checks re-resolve current authorization and recheck the fence. These code paths remain disabled by default; V8 migration, PostgreSQL concurrency, deployed IAM and end-to-end Process/Agent behavior have not yet been accepted.

The linked adapter is enabled separately with `stellar.tianji.agent.linked.enabled=true` and requires the secured Agent API, V7 and at least one operator-owned binding of exact issuer, tenant, SERVICE client/app/business/environment tuple, process source and allowed scope type. Its `/api/tianji/v1/agent-process-dispatches/resolve` and `/close` operations require the distinct `tianji:agent:linked:resolve` and `tianji:agent:linked:close` scopes and their permission resources. Submission also requires an exact allowlisted Agent definition/version/hash and `tianji:agent:linked:submit`; it remains disabled unless `submission-enabled=true` and a host supplies `TianjiLinkedServiceAdmission`. The opt-in V8 service-execution configuration supplies an admission that persists a revocable SERVICE grant. If admission fails after the queued run commits, the caller can resolve or close the same link and retry with the same key. Building the manifest does not register or grant these resources.

`HttpLinkedAgentClient` implements the engine-neutral linked contract. The host supplies a SERVICE token for each operation, a JDK `HttpClient` with redirects disabled, and a total timeout covering bounded token acquisition and the HTTP exchange. It accepts HTTPS or loopback HTTP, limits request and response bodies, checks the echoed idempotency key and complete process link, and treats a 404 as an error rather than proof that no submission exists. Submit and close are sent once at the application level; an uncertain result must be resolved or closed with the same link rather than assumed absent. Closing the client cancels in-flight transport calls but does not cancel an Agent run. Timed-out token providers that ignore interruption can occupy one of the limited token slots until they return.

The default-off `stellar.tianji.agent.execution-authorization.enabled` switch provides an `AgentRunAuthorization` implementation for sealed USER intents and, when separately enabled, linked SERVICE intents. It requires grant issuance to be enabled, the existing Jianshen system/endpoint/resource settings, and the same tenant SERVICE registration used for issuance with the separate `service:authorization:execution` scope. The verifier checks the stored intent and current Jianshen decision before claim and before each model call, then rechecks the ticket, issuer trust and database clock before accepting the result. Only a confirmed denial against the unchanged ticket becomes `DENY`; missing, expired, changed or unavailable evidence becomes `UNAVAILABLE`. SERVICE runs additionally require the explicit V8 service-execution configuration and matching Shoubing/Jianshen policies; legacy runs remain unavailable. `timeout-ms` defaults to 10000 (100–30000) and `concurrency` to 4 (1–8); a bounded, no-queue virtual-thread executor limits the entire check, including SERVICE token acquisition. Timed-out dependency calls that ignore interruption can occupy a slot until they return. Identity and RBAC checks are separate transactions, so revocation cannot be atomic with a later model call. Enabling this verifier does not start a dispatcher or configure a model estimator.

The default-off `stellar.tianji.agent.dispatch.enabled` switch enables rotating discovery of queued USER runs with unexpired sealed evidence; it also discovers linked SERVICE runs only when the matching service authorizer is enabled. LEGACY runs are excluded. It requires a dedicated `AgentRunDispatcher` using the exact `TianjiExecutionGrantAuthorizer`, a `TaskScheduler` named `tianjiAgentDispatchScheduler`, and an enabled reconciler with its own `tianjiAgentReconciliationScheduler`. The standalone server provides the two schedulers when needed; a host may provide its own. Discovery, dispatcher, worker, authorizer, grant store and reconciler must share the exact same ledger instance. The reconciler starts before dispatch and stops after it; failure to start reconciliation prevents dispatch from starting. The runtime switch above can assemble the dispatcher, or a host may wire it explicitly. `batch-size` defaults to 64 (1–1000), `max-in-flight` to 4 (1–128), `interval-ms` to 2000 (250–3600000), and `shutdown-timeout-ms` to 5000 (0–30000). Discovery advances through a keyset cursor so an unavailable run does not permanently pin the queue; admission is bounded even when the host executor queues tasks. Each worker still rechecks authorization and claims with the database lease/CAS. Stopping the poller closes its dedicated dispatcher and waits up to the configured timeout; Spring manages the server's schedulers and executors. No scheduler is started by the build.

Linked terminal publication has a separate default-off switch, `stellar.tianji.agent.terminal-events.enabled`. The `AgentTerminalEvent` contract carries the exact process link, service owner, definition, terminal revision/status and a digest of the stored result; it contains no model output, bearer or native execution ID. Its 64-character event ID remains stable for the same producer/owner/run/revision, and its canonical envelope fingerprint detects a changed duplicate independently of JSON property order. The result stays in the Agent ledger and requires authorized retrieval; the digest identifies the persisted representation and is not a hash of arbitrary HTTP response bytes.

`AgentLedgerService.withTerminalEvents` accepts a synchronous publisher using the exact same DataSource. The centralized status-event path publishes only after a linked run reaches a terminal state, including leased completion/failure/cancellation/timeout and deadline reconciliation. Running cancellation intent and authorization suspension are not terminal events. It rechecks the fixed definition, result and original dispatch-fence association before publication; publisher failure propagates through the ledger transaction. Existing constructors remain opted out. The server's `OutboxAgentTerminalEventPublisher` is an Adapter to the existing transactional Outbox; the runtime and public contract have no Outbox dependency. It enqueues a compact reference with the same event ID/idempotency key and a fixed logical source-to-destination mapping, then validates the receipt. Publication performs no HTTP call.

Enabling that server adapter requires `storage.enabled=true`, explicit JDBC Outbox enablement, schema validation and schema `tianji_agent`, disabled startup Flyway/SQL initialization, a fixed `terminal-events.producer-id`, and a nonempty `terminal-events.destinations` map. Provision the existing component's `db/transactional-outbox/postgresql/V1__create_transactional_outbox_schema.sql` through a separate operator-owned history such as `tianji_agent_outbox_schema_history`; do not reuse the Agent migration history or change an earlier Agent migration. On a nonempty schema the operator must inspect existing objects and establish any required baseline deliberately. The adapter also requires a registered `tianji-agent-result` delivery handler for every logical destination. Authenticated HTTP delivery and the Process Inbox are not supplied by this publication step, so the server rejects activation without an appropriate handler. No settings, schema, permissions or runtime are automatically enabled by the build. Unit tests cover canonical IDs, Jackson 2/3 wire compatibility, storage/transaction guards and a mocked Outbox rollback request. The opt-in linked PostgreSQL test contains a transactional publisher fixture for ledger/status/fence rollback and all terminal paths; it is not proof of a deployed or real-Outbox transaction until explicitly run and extended through the delivery/Inbox path.

The session-aware executor acquires a session lease after claiming the run, renews both while executing, and releases the session lease after shutdown. A competing run fails explicitly with `TIANJI_SESSION_BUSY` before calling the model. Losing a session lease interrupts the model and leaves the run for normal lease reconciliation rather than recording success. Database tests exercise the adapter and executor with a real ADK Runner and a fake model; the runtime remains disabled by default. Apply V3 through the dedicated AgentDB migration process, not through the application at startup.

The opt-in Agent HTTP adapter provides session metadata operations at `/api/tianji/v1/agent-sessions`: `PUT` with a caller-supplied `sessionId` creates or returns the owned session without replacing its history; `GET` lists owned sessions; `GET /detail` queries one; `DELETE` removes one only when no run or lease is active. The identifier is a query parameter for the individual operations. The API returns metadata rather than native ADK events or state. Creation requires both `TIANJI_AGENT_START` and `TIANJI_AGENT_READ`; reading requires `TIANJI_AGENT_READ`; deletion requires `TIANJI_AGENT_READ` and the separately granted `TIANJI_SESSION_DELETE`, with their matching OAuth scopes. Registration and grants are separate deployment operations.

Session-backed run starts use `POST /api/tianji/v1/agent-runs/with-session`, whose single authorization decision requires both start and read permissions and scopes. The original `POST /api/tianji/v1/agent-runs` remains the one-shot endpoint and now rejects a non-null session ID; callers using raw HTTP for the previously accepted but unexecutable session request must switch paths. `HttpAgentClient.start` selects the correct path automatically, and its `AgentSessionClient` methods send each mutation once without application-level replay. A client can repeat the same create ID after an uncertain response; after an uncertain delete it should query the session before deciding what to do next.

## Process Server storage baseline

The Process Server owns a separate PostgreSQL database/schema and shares one local `DataSource` and transaction manager between its Flowable engines and JDBC Outbox. Its default schema is `tianji_process`; configure the JDBC connection's search path to select that same schema. Startup rejects a different schema, transaction manager or data source, disabled Outbox validation, automatic Flowable schema changes, Spring SQL initialization and automatic Flyway migration. The process API is disabled by default, and a servlet host without it only exposes health. The Flowable IDM and Event Registry engines, automatic definition deployment, asynchronous job executors and Outbox polling are disabled by default. No Outbox delivery channel is configured yet. Disabling polling does not suppress the component's immediate post-commit wake-up; configure and verify a delivery channel before enqueuing production messages.

Before deployment, an operator must provision a dedicated schema with Flowable 8.0.0's official PostgreSQL schema/upgrade artifacts and the Outbox starter's unchanged `db/transactional-outbox/postgresql/V1__create_transactional_outbox_schema.sql`, using separate controlled migration histories and a schema owner. Configure a runtime role without schema creation privileges; the application never initializes or upgrades those tables, but does not create or manage database roles. This repository does not yet provide a production schema-provisioning command; the integration test initializes only its isolated empty database. The Process Server must not use the Agent-owned schema or tables; a separate logical database is preferred. Outbox messages require a tenant-scoped idempotency key and a trusted tenant in the event; delivery remains at least once.

The engines do not expose Spring beans to model expressions. `ProcessModelValidator` validates bounded UTF-8 XML against packaged Flowable schemas and a closed allowlist before release deployment. Its BPMN subset supports acyclic start/end, user tasks, bounded parallel gateways, constant timers and separately gated Worker, decision and Agent Message-wait shapes described below. DMN supports one decision table with string, boolean and at most 15-digit integer literals, and FIRST/UNIQUE/ANY hit policies. Decimal rules and CMMN imports require later validation. Flowable 8's ordinary decision builder can fall back to the latest same-tenant definition when a parent deployment is missing, and the tested audit result does not populate its deployment ID; that builder alone cannot enforce a fixed release.

The optional decision-task subset adds one Flowable DMN service task and a bounded exclusive split immediately after it. The task references a decision by a literal `decisionTableReferenceKey`; both models must belong to the same immutable release. Each decision input must have the same name and type in the process input schema, and outputs must not overwrite process inputs. A split has an explicit default and only equality comparisons between one declared decision output and bounded primitive literals. Scripts, arbitrary expressions, other extension fields, parallel gateways in a decision-task model and unsupported graph shapes are rejected. On no hit, decision outputs are set to null and the default route is used. Equal multi-hit outputs are accepted; inconsistent outputs fail the transaction. The exact process and decision definitions, tenant, version and model hashes are rechecked at execution, and decision history is committed with the process transition. The fixture `approval-routing.bpmn20.xml` illustrates the supported form.

Publishing models with decision tasks is disabled by default. Set `stellar.tianji.process.decision-tasks.enabled=true` on API nodes only after **all** Process Server nodes, including timer and job executors, run a version containing the pinned decision behavior and have synchronous DMN history enabled. Existing published instances can continue when publication is disabled. DMN tasks deployed outside a Tianji release cannot be resolved by the pinned behavior and fail closed; inventory and migrate any such unmanaged instances before upgrading. Do not run or roll back to an older Process Server after enabling this feature: an older engine can use Flowable's latest-version fallback. This switch does not register permissions or enable the Process API.

The internal `FlowablePinnedDecisionExecutor` replaces that fallback with an exact definition-ID lookup inside Flowable's command, checks the bound tenant, key, deployment, version and validated XML, then checks the decision audit inside the same JDBC transaction. It accepts only the validated input names and primitive types, returns immutable values and rolls back a failed decision. Its binding must come from a separately authorized tenant-scoped release; the adapter does not grant access, manage releases or expose an HTTP/SDK endpoint.

The internal `ProcessReleaseService` atomically deploys validated BPMN/DMN resources and records immutable, tenant-scoped definition IDs, versions, model hashes and input schemas. An identical release key and manifest is idempotent; a different manifest conflicts. It serializes concurrent deployments of the same tenant/model key so Flowable versions remain distinct.

The platform release/command tables have separate migrations under `db/tianji-process`: V1 creates release and receipt tables, V2 adds decision result receipts, and V3 binds publisher and command ownership to an issuer fingerprint without changing earlier migrations. Use the `tianji_process_schema_history` Flyway history for this location, distinct from Outbox's history and Flowable's own schema history. Because the shared schema already contains engine and Outbox tables, the isolated integration test explicitly creates the new history with a version-0 baseline before applying platform V1. Production provisioning requires an operator-controlled equivalent after checking the target history and platform tables; the application still performs no automatic migration.

V3 retains pre-existing ownership in a separate `LEGACY` namespace. New HTTP identities use a fingerprint of the verified issuer and cannot automatically claim those records. Upgrade every process reader and writer before enabling the API; old binaries that ignore issuer affinity must not run alongside new issuer-bound writes. If legacy records need to become available to verified identities, an operator must first establish an authoritative mapping and plan a separate controlled migration. V3 changes the receipt primary key and therefore needs an appropriately planned database migration window.

The internal `ProcessExecutionService` starts a process by the exact tenant-scoped release binding after rechecking its deployed model and input schema. The start receipt and Flowable instance commit together; the same actor and command ID replay the existing instance, while changed input conflicts. Its query is restricted to the initiating actor and tenant and uses synchronous Flowable instance history for completed or cancelled instances.

The internal `ProcessDecisionService` evaluates a release-bound DMN without creating a BPMN instance. It stores the decision's scoped history and result receipt in the same transaction, so a repeated actor/request ID returns the original result without evaluating again. Rule IDs come from the model; a rule without an explicit ID is identified by its stable `row:<one-based number>` within that immutable release. Decision input values are present in Flowable's decision history; retention and redaction controls remain future work.

Set `stellar.tianji.process.api.enabled=true` only in an explicitly configured servlet host. The source provides `POST /api/tianji/v1/process-releases`, `GET /api/tianji/v1/process-releases/{releaseVersion}`, `POST /api/tianji/v1/process-instances`, `GET /api/tianji/v1/process-instances/{instanceId}` and `POST /api/tianji/v1/decisions/evaluate`. The adapter requires verified Tianquan-Shoubing USER or tenant-scoped SERVICE identity, the Tianquan-Jianshen guard, and respectively `TIANJI_PROCESS_RELEASE_PUBLISH`, `TIANJI_PROCESS_RELEASE_READ`, `TIANJI_PROCESS_START`, `TIANJI_PROCESS_READ`, or `TIANJI_DECISION_EXECUTE` with their matching OAuth scopes. Tenant, subject and issuer never come from request bodies; instance reads remain owner-scoped. Registration, activation and role/client grants are separate deployment steps and are not performed by the build.

The current checks cover the resource permission, OAuth scope, tenant and instance owner. Business-specific object and data scopes are not yet applied.

The engine-neutral Worker contract and HTTP client define one-task acquisition and completion/failure receipts. The opt-in Process Server endpoints are `POST /api/tianji/v1/worker-tasks/acquire`, `/complete` and `/fail`. They accept only verified SERVICE identities: acquire requires `TIANJI_WORKER_ACQUIRE` and `tianji:worker:acquire`; complete/fail require `TIANJI_WORKER_REPORT` and `tianji:worker:report`. Acquisition derives tenant from the verified identity, and an uncertain acquisition may leave a lease until it expires. An accepted completion or failure can be replayed with the exact same lease and payload; a lost lease returns HTTP 409 with `TIANJI_WORKER_LEASE_LOST`, while a different payload for an accepted receipt returns `TIANJI_IDEMPOTENCY_CONFLICT`. An unknown side effect requires manual reconciliation. A receipt ID alone does not prove business idempotency: the Worker integration must commit the business change and its receipt in the same business transaction or use an external system's verified idempotency mechanism. Lease tokens and task data are redacted from the contract objects' string representations.

The validator recognizes an external-worker model with a literal logical topic, a schema version, an effect-safety mode, `doNotIncludeVariables=true` and explicit typed input/output mappings, illustrated in `worker-mapping.bpmn20.xml`. Its Flowable topic must be `logical-topic:schema-version`; the separator cannot appear in either part, so incompatible versions have separate native queues. The current mapping check allows inputs only from declared process inputs and rejects output names that overwrite those inputs or other decision/worker outputs. The public release endpoint rejects these models unless Worker is explicitly enabled and an operator-controlled registry authorizes the exact mappings.

ProcessDB migration V4 adds the Worker lease and receipt table without changing earlier migrations. The internal JDBC store binds each lease to a verified service issuer, subject, tenant and native job; stores only a hash of the lease token; limits the database-timed expiry to the native lock and configured duration; and retains accepted receipts for exact replay. The store requires the caller's transaction and does not itself lock or verify a Flowable job. The existing Process API continues to verify V1–V3; enabling Worker additionally verifies V4. Apply V4 through the operator-controlled ProcessDB migration process, never automatically at application startup.

The Flowable Worker adapter currently handles BPMN jobs. It adds native-job locking and rechecks the release, topic, mapped input, effect-safety mode and output schema before accepting a completion. Its operator-provided registry binds exact tenant, verified issuer, service subject, topic and version, explicitly permits process-variable sources and output targets, limits leases per registration and caps each service identity at 32 live leases. A change to the registration policy during a lease prevents that lease from completing until it is reconciled. Acquisition requires the native async executor and expired-job reset to be active; completion creates a native async job before the process advances. Retryable failures follow the configured delay and native retry budget, while unknown outcomes and business rejections enter Flowable's dead-letter state for manual recovery. CMMN Worker execution, dynamic registration, permission grants, business receipt atomicity, real network behavior and multi-node configuration consistency still need implementation and acceptance.

The registry is an operator grant, not a worker-supplied claim. Register and activate the generated permission manifest and assign the required scopes and service permissions through the existing IAM process; building or setting this configuration does not grant them. The selected effect-safety mode is a contract that the business implementation must actually satisfy.

The `stellar-enclosure-tianji-worker-starter` module provides a PostgreSQL `JdbcWorkerExecutionStore` and an opt-in bounded poller. The store has been tested with a direct PostgreSQL primary DataSource, not a sharding proxy or replica. The host explicitly provisions `db/tianji-worker/V1__create_worker_execution_receipt.sql` in its business schema using a separate `tianji_worker_schema_history` history. On a nonempty schema, its baseline must be established by an operator after checking existing objects; the library never applies migrations automatically. The runtime role needs access to the receipt and business tables and read access to the history and PostgreSQL catalog. Each worker for the same Process Server and tenant must use the same stable `sourceId` and business database so retries share the receipt; unrelated Process Server histories must use different source IDs.

For `TRANSACTIONAL_RECEIPT`, the store compares the task's effect-safety mode and exact input/output schemas with the handler descriptor, executes the handler and receipt insert in one owned JDBC transaction, and replays the committed result on a duplicate intent. The receipt timestamp is sampled within that transaction and becomes visible only after commit; it is not a database commit timestamp. The handler is synchronous so that its work stays on the transaction-owning thread; it must use that same local transaction and must not perform external side effects or start an independent transaction.

`READ_ONLY` and `EXTERNAL_IDEMPOTENT` use `NonTransactionalWorkerRegistration` with a stable, operator-owned target ID and handler version. Before calling the handler, the store commits a durable intent binding the source, tenant, task, input, contract, target and handler version; no database transaction or lock is held during the call. The handler receives a deterministic external idempotency key scoped to the source, tenant and target. A read-only handler must not change external state. An external idempotent handler must send that key to an operation that atomically deduplicates identical requests and returns the same receipt and result, including after a lost response; a mere local retry is insufficient. The handler must enforce the supplied deadline on its own external calls. The first committed result becomes the replayable receipt; inconsistent external results fail for manual investigation. An uncertain outcome may be marked retryable only when the external idempotency contract actually holds. Pending intent blocks a different target, input or handler version; a completed receipt can be replayed after a handler upgrade. External work already started cannot be undone by lease expiry or cancellation.

These two modes require the separately provisioned `db/tianji-worker/V2__add_nontransactional_worker_intent.sql`. Before enabling them, stop and upgrade all Worker writers, apply V2, and grant every Worker role SELECT on the intent table; roles running these modes also need INSERT. Older writers do not check for a conflicting V2 intent and must not run concurrently. The store verifies V1 alone for transactional-only deployments and checks V2 before accepting non-transactional handlers. Intent rows are retained as deduplication evidence; retention and cleanup require a separate policy. The configured deadline safety margin must cover clock skew among the Process database, business database and Worker host and leave time for the acknowledgement. The Worker task wire contract requires `effectSafety`, `inputSchema` and `outputSchema`; upgrade the server and Worker clients together before enabling this unreleased capability.

Worker polling is disabled by default. To enable it in a business application, provide a `WorkerClient`, a `WorkerExecutionStore`, one or more `WorkerHandlerRegistration` or `NonTransactionalWorkerRegistration` beans, a host-managed `TaskScheduler` named `tianjiWorkerScheduler` and an `Executor` named `tianjiWorkerExecutor`. Set `stellar.tianji.worker.enabled=true` and `stellar.tianji.worker.tenant-id` to the same tenant as the store and service credential. `concurrency` defaults to 1 and is capped at 32; `poll-interval` defaults to 2 seconds. The default acknowledgement reserve and maximum clock skew are 3 and 2 seconds, so the store's deadline safety margin must be at least their sum. Acknowledgement attempts default to 2; shutdown waits up to 5 seconds by default. The poller does not create its own threads or credentials. A tenant or handler-contract mismatch stops polling, and an unconfirmed acknowledgement can be retried with the same receipt or replayed after a new lease.

The internal Process-side `AgentStartWorker` reuses the native Worker adapter and the engine-neutral `LinkedAgentClient`. Its operator-owned `AgentDispatchBinding` fixes the verified SERVICE actor, source ID, topic/schema, Agent key/version/content hash, instruction and 1-second to 15-minute submission window. Its host-provided registry registration must set `internalAgentDispatch=true`, use `EXTERNAL_IDEMPOTENT` and expose exactly one string output named `runId`; the registry controls its process-variable target. The ordinary acquire/complete/fail endpoints reject these internal registrations. Existing constructors default to ordinary Worker behavior, and all Process nodes must upgrade and use the same internal registration before these topics are published. Only the lease's validated mapped inputs become Agent task data. No model expression or Worker payload can select the Agent definition or occurrence.

This bridge requires the separately provisioned ProcessDB `V5__add_agent_dispatch_intent.sql`. `AgentDispatchStore` verifies V1–V5 and critical columns, constraints and indexes without applying DDL. Preparation commits a unique intent per native job occurrence, fixed input/routing digest and database-timed deadline before remote resolve/submit. Reacquisition preserves that deadline and resolves an unknown submission using the same key. A successful submission records its run ID; native Worker completion, its receipt and the `ACKNOWLEDGED` correlation state then commit in one Process transaction. `ACKNOWLEDGED` does not prove a Message subscription exists: native completion first schedules asynchronous advancement.

Cancellation, process completion or an unacknowledged submission deadline changes the intent to `CLOSING`. `reconcileOnce` must continue after stopping new acquisitions, including for unknown run IDs, until Agent returns a matching closed fence. A timeout or missing response never counts as closed. The fence can contain a run with cancellation requested; closure does not prove that a previously started external side effect has stopped. Bounded observations use database time and `SKIP LOCKED`; repeated or overlapping close calls use the same immutable query. The bridge rejects invocation inside a caller transaction and keeps remote calls outside its local transactions. The host owns a correctly authenticated bounded SERVICE client and scheduling. No bridge scheduler or public dispatch endpoint is enabled by this implementation; terminal Outbox/Inbox delivery and deployment wiring remain separate plan steps.

The validator also recognizes a fixed Agent wait shape, illustrated by the test fixture `agent-dispatch-wait.bpmn20.xml`: an internal Worker leads directly to an event-based gateway with exactly one literal Message catch and one constant Timer catch. The Message catch declares `tianji:workerRef` for that Worker. Message IDs and names are bounded local identifiers, each declaration is used once, and dynamic expressions, namespace-prefixed references, signal broadcasts and additional event definitions are rejected. Immutable validation metadata identifies the Worker, Message name, Timer element and maximum wait. Publication requires V5, an internal topic registry and the explicit six-argument `ProcessReleaseService` constructor with `agentMessageWaitsEnabled=true`; existing constructors and the public server configuration keep this disabled. Internal topics require a matching wait, and runtime lease validation rejects a changed ordinary/internal registration. The fixed Flowable converter is covered without a database. The native Message subscription, competing Timer cancellation, exact execution delivery and rollback scenario are in the opt-in Process PostgreSQL test and remain unexecuted without that database. Terminal Inbox delivery and a durable close transition when the Timer path wins still need implementation before enabling this bridge in a deployment.

Service permission is checked on acquisition and on each report. A permission change after acquisition cannot undo a business transaction already in progress; the lease bounds that window, and the business handler remains responsible for its own object-level authorization.

Enabling the API performs read-only checks of platform Flyway checksums, columns, key constraints and the start receipt index; the runtime role needs SELECT on `tianji_process_schema_history` and the PostgreSQL catalog. These checks and the engine/API integration have been exercised against PostgreSQL 18.3; other PostgreSQL versions and real identity/permission services require separate acceptance. The adapter bounds Process JSON bodies to 9 MiB and Worker bodies to 256 KiB, rejects unknown Worker fields and duplicate keys, and does not install schema or publish permissions at startup.
